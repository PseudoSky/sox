# SPEC — `@adhd/sox-task-queue`

> General-purpose durable task queue over SQLite: priority-aware FIFO scheduling,
> retry with exponential backoff, heartbeat-based lease management, worker pool
> with graceful shutdown, and a cron scheduler for recurring tasks.

## 1. Use cases & design drivers

Three generalized use cases motivate the interface:

| Use case | Concurrency | Task count | Retry need | Scheduling need | Durability requirement |
|---|---|---|---|---|---|
| **CLI tool with background jobs** | Single process, multiple concurrent handlers | 100s–10,000s | Yes (transient API failures) | No (one-shot tasks enqueued by user) | Survive CLI process restart mid-job |
| **Embedded service with recurring maintenance** | Single process, dedicated worker | 10s of cron-like tasks | No (tasks are idempotent maintenance) | Yes (every 5 min, daily at midnight) | Survive service restart; cron state is persistent |
| **API server with offline work fan-out** | Single process, high concurrency | 100,000s | Yes (3 retries for external API calls) | Optional (delayed processing) | Survive server crash; no task is lost |

**Cross-cutting requirements:**
- All state is in SQLite — no external message broker, no Redis, no in-memory-only queue
- Durability guarantee: a task that is `enqueue`d has been committed to SQLite before the Promise resolves
- At-least-once execution: every queued task is executed at least once; duplicates are possible on crash recovery (caller must handle idempotency)
- Priority ordering: higher-priority tasks are dequeued before lower-priority ones; same-priority tasks are FIFO
- Heartbeat lease: a task that is claimed but never completed is automatically re-queued after its heartbeat lease expires
- Graceful shutdown: on `close()`, the queue drains in-flight tasks before resolving
- Zero external runtime dependencies beyond `better-sqlite3` and the cron parser (`croner`)

## 2. Core types

```ts
// ── TaskStatus ─────────────────────────────────────────────────────────────────

enum TaskStatus {
  Queued       = 'queued',
  Running      = 'running',
  Completed    = 'completed',
  Failed       = 'failed',        // retries exhausted → dead
  Cancelled    = 'cancelled',
  Scheduled    = 'scheduled',     // waiting for scheduled_at to arrive
}

// ── Task ───────────────────────────────────────────────────────────────────────

interface Task<T = unknown> {
  id: string                       // UUIDv4, generated by enqueue if omitted
  type: string                     // Logical task type for routing (e.g. 'reembed', 'email-send')
  status: TaskStatus
  priority: number                 // Higher = more urgent. Default: 0. Range: -128 to 127.
  payload: T                       // Application-specific data. Must be JSON-serializable.
  retryCount: number               // Current retry attempt (0 = first execution)
  maxRetries: number               // 0 = no retries. Default: 3.
  scheduledAt: string | null       // ISO 8601. null = execute immediately on dequeue.
  created_at: string               // ISO 8601. Set at enqueue time.
  started_at: string | null        // ISO 8601. Set when a worker claims the task.
  completed_at: string | null      // ISO 8601. Set on complete or fail (terminal).
  error: string | null             // Last error message. null on success.
  dead: boolean                    // true when maxRetries exhausted. Terminal.
  clientRequestId: string | null   // Idempotency key for dedup enqueue (see §7).
  result: string | null            // JSON-serialized result from the handler.
  leaseExpiresAt: string | null    // ISO 8601. Deadline for the current lease.
  workerId: string | null          // ID of the worker currently holding the lease.
  ttlMs: number | null             // Max wall-clock time before the task auto-fails.
}

// ── TaskQueueConfig ────────────────────────────────────────────────────────────

interface TaskQueueConfig {
  // Path to the SQLite database file. ':memory:' is valid for testing.
  dbPath: string

  // Maximum tasks to return in a single dequeue batch. Default: 10.
  dequeueBatchSize?: number

  // Default maxRetries for tasks that don't specify one. Default: 3.
  defaultMaxRetries?: number

  // Heartbeat lease duration in milliseconds. The worker must heartbeat within
  // this window or the task is re-queued. Default: 30_000 (30 s).
  heartbeatTimeoutMs?: number

  // Maximum wall-clock time before a task auto-fails. Overrides task-level ttlMs.
  // null = no global limit. Default: null.
  defaultTtlMs?: number | null

  // Whether to enable automatic re-queue of expired leases.
  // When false, expired tasks remain in 'running' state until manually resolved.
  // Default: true.
  autoRequeueExpired?: boolean

  // Interval in milliseconds for the lease expiry reaper tick. Default: 5_000 (5 s).
  reaperIntervalMs?: number
}

// ── TaskFilter ─────────────────────────────────────────────────────────────────

interface TaskFilter {
  status?: TaskStatus | TaskStatus[]
  type?: string | string[]
  priorityMin?: number
  priorityMax?: number
  dead?: boolean
  createdAfter?: string
  createdBefore?: string
  scheduledBefore?: string          // only tasks with scheduled_at <= this
  limit?: number
  offset?: number
  orderBy?: 'created_at' | 'priority' | 'scheduled_at'
  orderDir?: 'asc' | 'desc'
}

// ── QueueStats ─────────────────────────────────────────────────────────────────

interface QueueStats {
  byStatus: Record<TaskStatus, number>
  total: number
  deadCount: number
  runningCount: number
  avgProcessingLatencyMs: number    // rolling average of completed - started
  retryDistribution: Record<number, number>  // retryCount → count of live tasks
  oldestQueuedAgeMs: number         // age of the oldest 'queued' task
  heartbeatMisses: number           // count of tasks re-queued due to expired lease
  enqueueCount: number              // lifetime enqueues for this instance
  dequeueCount: number              // lifetime dequeues for this instance
  completeCount: number             // lifetime completions for this instance
  failCount: number                 // lifetime terminal failures for this instance
}

// ── EnqueueResult ──────────────────────────────────────────────────────────────

interface EnqueueResult {
  id: string
  deduplicated: boolean             // true if this task was rejected as duplicate
  isNew: boolean                    // true if this is a fresh enqueue
}

// ── DequeueResult ──────────────────────────────────────────────────────────────

interface DequeueResult {
  task: Task
  // The worker must call complete/fail/heartbeat before the lease expires.
  // The lease is automatically extended on heartbeat.
}
```

## 3. `TaskQueue` — primary interface

```ts
interface TaskQueue {
  // ── Lifecycle ────────────────────────────────────────────────────────────────

  // Open the database, apply schema, start the lease expiry reaper.
  // Must be called before any other method. Idempotent.
  open(): Promise<void>

  // Graceful shutdown: wait for in-flight tasks to complete (up to drainTimeoutMs),
  // then stop the reaper and close the database.
  // THROWS QueueShutdownTimeout if tasks are still running after drainTimeoutMs.
  close(opts?: { drainTimeoutMs?: number }): Promise<void>

  // Returns true between open() and close().
  readonly isOpen: boolean

  // ── Enqueue ──────────────────────────────────────────────────────────────────

  // Enqueue a single task. Returns the task ID.
  // If task.id is omitted, a UUIDv4 is generated.
  // If clientRequestId is set and a task with the same clientRequestId exists,
  // the enqueue is a no-op (returns the existing task's ID with deduplicated: true).
  // THROWS QueueFullError if the queue has reached its maximum depth (if configured).
  enqueue(task: Partial<Task> & { type: string; payload: unknown }): Promise<EnqueueResult>

  // Enqueue multiple tasks atomically (single SQLite transaction).
  // All tasks are committed or none are. Returns results in the same order.
  // THROWS QueueFullError if any task would exceed the queue depth limit.
  enqueueBatch(tasks: Array<Partial<Task> & { type: string; payload: unknown }>): Promise<EnqueueResult[]>

  // ── Dequeue ──────────────────────────────────────────────────────────────────

  // Atomically claim the next eligible task(s) for processing.
  // Eligibility: status = 'queued' OR (status = 'scheduled' AND scheduled_at <= now).
  // Ordered by priority DESC, then created_at ASC (FIFO within priority).
  // Sets status = 'running', started_at = now, leaseExpiresAt = now + heartbeatTimeoutMs.
  // Sets workerId = provided workerId.
  // Returns up to dequeueBatchSize tasks. Empty array if no eligible tasks.
  // THROWS TaskQueueSystemError on DB failure.
  dequeue(workerId: string): Promise<DequeueResult[]>

  // ── Completion ───────────────────────────────────────────────────────────────

  // Mark a task as completed successfully.
  // Sets status = 'completed', completed_at = now.
  // Stores result as JSON string.
  // THROWS TaskNotFoundError if the task does not exist.
  // THROWS TaskNotRunningError if the task is not in 'running' status.
  complete(taskId: string, result?: unknown): Promise<void>

  // Mark a task as failed. Increments retryCount.
  // If retryCount < maxRetries: re-queues with status = 'queued', clears workerId/lease.
  //   The scheduled_at is set to now + backoffDelay (see §9).
  // If retryCount >= maxRetries: sets dead = true, status = 'failed'.
  // Stores error as string.
  // THROWS TaskNotFoundError if the task does not exist.
  // THROWS TaskNotRunningError if the task is not in 'running' status.
  // THROWS TaskPermanentlyFailedError if the task was already dead (terminal).
  //   (This is defensive — if the caller sees this, their handler is running a dead task.)
  fail(taskId: string, error: string): Promise<void>

  // ── Heartbeat ────────────────────────────────────────────────────────────────

  // Refresh the lease for a running task. Extends leaseExpiresAt to now + heartbeatTimeoutMs.
  // Returns true if the task is still running (lease extended).
  // Returns false if the task has been cancelled or re-queued (lease expired).
  // THROWS TaskNotFoundError if the task does not exist.
  heartbeat(taskId: string): Promise<boolean>

  // ── Cancellation ─────────────────────────────────────────────────────────────

  // Best-effort cancel a task.
  // If status = 'queued' | 'scheduled': set status = 'cancelled', terminal.
  // If status = 'running': set a cancellation flag; the worker must check
  //   isCancelled(taskId) to honour cancellation mid-execution.
  // If status is terminal (completed, failed, cancelled): no-op.
  // Returns true if the task was successfully cancelled, false if already terminal.
  cancel(taskId: string): Promise<boolean>

  // Check whether a running task has been cancelled. Workers poll this between
  // long-running operations. Returns true if the task was cancelled after dequeue.
  isCancelled(taskId: string): Promise<boolean>

  // ── Query ────────────────────────────────────────────────────────────────────

  // Get a single task by ID. Returns null if not found.
  get(taskId: string): Promise<Task | null>

  // List tasks matching a filter. Returns paginated results.
  listTasks(filter?: TaskFilter): Promise<Task[]>

  // Return aggregate queue statistics.
  stats(): Promise<QueueStats>

  // Count tasks matching the filter.
  countTasks(filter?: TaskFilter): Promise<number>

  // ── Admin / Maintenance ──────────────────────────────────────────────────────

  // Purge completed tasks older than the given age.
  // Returns the count of purged rows.
  purgeCompleted(olderThanMs: number): Promise<number>

  // Reset a failed (dead) task back to 'queued' for manual retry.
  // Resets retryCount to 0, clears error, clears dead flag.
  // THROWS TaskNotFoundError.
  // THROWS TaskNotDeadError if the task is not in a dead state.
  requeue(taskId: string): Promise<void>

  // Remove all tasks matching a filter. Idempotent.
  // THROWS QueueNotEmptyError if any matching tasks are 'running'.
  deleteTasks(filter: TaskFilter): Promise<number>
}
```

## 4. Worker pool

```ts
// ── WorkerPoolConfig ───────────────────────────────────────────────────────────

interface WorkerPoolConfig {
  // The queue instance to pull tasks from.
  queue: TaskQueue

  // Task handler function. Called with each dequeued task.
  // Must return void (success → complete) or throw (→ fail).
  handler: (task: Task) => Promise<void>

  // Maximum number of concurrent task executions. Default: 1.
  concurrency?: number

  // Poll interval in milliseconds when no tasks are available. Default: 1_000 (1 s).
  pollIntervalMs?: number

  // Heartbeat interval in milliseconds. The pool sends a heartbeat for each
  // running task on this cadence. Default: heartbeatTimeoutMs / 3.
  heartbeatIntervalMs?: number

  // Maximum time in milliseconds to wait for running handlers to finish during
  // graceful shutdown. Default: 30_000 (30 s).
  drainTimeoutMs?: number

  // Name for this worker pool instance (used as workerId in lease).
  // Default: auto-generated UUID.
  workerName?: string

  // If true, the pool starts polling immediately. If false, call start().
  // Default: true.
  autoStart?: boolean
}

// ── WorkerPool interface ───────────────────────────────────────────────────────

interface WorkerPool {
  // Start polling for tasks. No-op if already started.
  start(): void

  // Graceful shutdown:
  // 1. Stop polling for new tasks.
  // 2. Wait for running handlers to complete (up to drainTimeoutMs).
  // 3. Resolve.
  // Running tasks that exceed drainTimeoutMs are abandoned (lease will expire
  // and the reaper will re-queue them).
  stop(): Promise<void>

  // Whether the pool is currently polling.
  readonly isRunning: boolean

  // Current number of active handlers.
  readonly activeCount: number

  // Lifetime stats for this pool instance.
  readonly stats: {
    tasksProcessed: number
    tasksFailed: number
    tasksTimedOut: number
  }
}

// ── Factory ────────────────────────────────────────────────────────────────────

function createWorkerPool(config: WorkerPoolConfig): WorkerPool
```

### Worker pool lifecycle

```
createWorkerPool(config)
    │
    ▼
start() → poll loop begins
    │
    ├── dequeue() → handler(task) → complete() or fail()
    │       │                          │
    │       └── heartbeat() loop ◄─────┘
    │              (every heartbeatIntervalMs)
    │
    ├── no tasks → wait pollIntervalMs → retry
    │
    └── stop() called
            │
            ▼
        stop polling → wait draining handlers → resolve
```

**Handler error handling:**
- If the handler throws, the pool calls `queue.fail(taskId, error.message)`.
- If `fail()` throws (e.g., task not found or not running), the pool logs a warning
  and moves on — the task is in an inconsistent state and must be reconciled manually.
- If the handler times out (exceeds `ttlMs`), the pool does NOT auto-fail the task;
  the lease reaper handles TTL-based expiry. The handler Promise is abandoned
  (no cancellation — the handler continues running but its result is ignored).

## 5. Scheduler

```ts
// ── SchedulerConfig ────────────────────────────────────────────────────────────

interface SchedulerConfig {
  // The queue instance to enqueue scheduled tasks into.
  queue: TaskQueue

  // Default task type for scheduled tasks. Can be overridden per-entry. Default: 'scheduled'.
  defaultType?: string

  // Default priority for scheduled tasks. Default: 0.
  defaultPriority?: number

  // Default maxRetries for scheduled tasks. Default: 0 (no retries for cron tasks).
  defaultMaxRetries?: number

  // Poll interval in milliseconds. The scheduler checks for due cron expressions
  // on this cadence. Default: 1_000 (1 s).
  tickIntervalMs?: number

  // Auto-start the tick loop. Default: true.
  autoStart?: boolean
}

// ── ScheduledEntry ─────────────────────────────────────────────────────────────

interface ScheduledEntry {
  id: string                       // UUIDv4, auto-generated
  name: string                     // Human-readable label. Must be unique.
  taskType: string                 // Task type for the enqueued task.
  payload: unknown                 // Payload for the enqueued task. Must be JSON-serializable.
  cronExpression: string           // Standard cron syntax. Backend: croner.

  // Optional overrides for the enqueued task.
  priority?: number
  maxRetries?: number
  ttlMs?: number | null

  // If true, on scheduler start, the first enqueue immediately fires
  // (even if the cron would not have fired yet). Useful for boot-time
  // maintenance tasks. Default: false.
  runOnStart?: boolean

  // Whether this entry is active. Inactive entries are skipped on tick. Default: true.
  enabled: boolean

  // Audit timestamps.
  created_at: string
  updated_at: string
  lastEnqueuedAt: string | null    // When this entry last fired
  lastError: string | null         // Last error from enqueue
}

// ── Scheduler interface ────────────────────────────────────────────────────────

interface Scheduler {
  // ── Lifecycle ────────────────────────────────────────────────────────────────

  // Open the scheduler database, load entries, start the tick loop.
  open(): Promise<void>

  // Stop the tick loop and close the database.
  close(): Promise<void>

  // ── Entry management ─────────────────────────────────────────────────────────

  // Register a new cron entry. Persisted to SQLite.
  // THROWS SchedulerEntryConflictError if name already exists.
  register(entry: Omit<ScheduledEntry, 'id' | 'created_at' | 'updated_at' | 'lastEnqueuedAt' | 'lastError'>): Promise<ScheduledEntry>

  // Update an existing entry by ID. Overwrites all fields.
  update(id: string, entry: Partial<ScheduledEntry>): Promise<ScheduledEntry>

  // Remove an entry by ID.
  unregister(id: string): Promise<void>

  // Enable or disable an entry without changing other fields.
  enable(id: string, enabled: boolean): Promise<void>

  // ── Query ────────────────────────────────────────────────────────────────────

  // Get a single entry by ID.
  get(id: string): Promise<ScheduledEntry | null>

  // List all registered entries.
  list(): Promise<ScheduledEntry[]>

  // ── Manual trigger ───────────────────────────────────────────────────────────

  // Force-fire an entry immediately, regardless of its cron schedule.
  // Returns the enqueued task ID.
  triggerNow(id: string): Promise<string>

  // ── Status ───────────────────────────────────────────────────────────────────

  readonly isRunning: boolean
  readonly nextTickAt: string | null  // ISO 8601 of the next scheduled tick
}
```

### Scheduler tick algorithm

```
tick()
  │
  ├── For each enabled entry:
  │     ├── Compute next cron fire time (croner).
  │     ├── If lastEnqueuedAt < cronNextFireAt AND now >= cronNextFireAt:
  │     │     └── Enqueue task with taskType + payload from entry
  │     │         → update lastEnqueuedAt
  │     └── If cronNextFireAt is null (expired cron): disable entry
  │         with a logged warning.
  │
  └── Schedule next tick after tickIntervalMs
```

**Cron backend choice — `croner`:**
- MIT license, zero dependencies, supports standard cron + optional seconds
- Correctly handles DST transitions, timezone offsets, and leap years
- Smaller install size than `node-cron` (which bundles a patched `moment`)
- Used in preference to `node-cron` because `node-cron` has unresolved DST bugs and no timezone support

## 6. SQLite schema

```sql
-- Opens with WAL journal mode, 5s busy timeout, NORMAL synchronous,
-- and foreign keys enabled — following @adhd/sox-graph-store convention.

PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;
PRAGMA cache_size = -64000;

-- ── Core tasks table ──────────────────────────────────────────────────────────

CREATE TABLE IF NOT EXISTS tasks (
  id                TEXT    PRIMARY KEY,                          -- UUIDv4
  type              TEXT    NOT NULL,                             -- logical task type
  status            TEXT    NOT NULL DEFAULT 'queued'
                          CHECK (status IN ('queued','running','completed','failed','cancelled','scheduled')),
  priority          INTEGER NOT NULL DEFAULT 0,                   -- -128 to 127; higher = more urgent
  payload           TEXT    NOT NULL,                             -- JSON
  retry_count       INTEGER NOT NULL DEFAULT 0,
  max_retries       INTEGER NOT NULL DEFAULT 3,
  scheduled_at      TEXT,                                         -- ISO 8601; NULL = immediate
  created_at        TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  started_at        TEXT,                                         -- ISO 8601, set on dequeue
  completed_at      TEXT,                                         -- ISO 8601, set on complete/fail terminal
  error             TEXT,                                         -- last error message
  dead              INTEGER NOT NULL DEFAULT 0,                   -- boolean: maxRetries exhausted
  result            TEXT,                                         -- JSON result
  lease_expires_at  TEXT,                                         -- ISO 8601; NULL when not running
  worker_id         TEXT,                                         -- who holds the lease
  ttl_ms            INTEGER,                                     -- null = no TTL
  client_request_id TEXT    UNIQUE                                -- idempotency key (nullable)
) STRICT;

-- ── Indexes ────────────────────────────────────────────────────────────────────

-- Fast dequeue: find eligible tasks ordered by priority then creation time.
CREATE INDEX IF NOT EXISTS idx_tasks_dequeue
  ON tasks(priority DESC, created_at ASC)
  WHERE status IN ('queued', 'scheduled');

-- Fast lookup by type + status (for listTasks filters).
CREATE INDEX IF NOT EXISTS idx_tasks_type_status
  ON tasks(type, status);

-- Fast lookup of running tasks for heartbeat and reaper.
CREATE INDEX IF NOT EXISTS idx_tasks_running
  ON tasks(lease_expires_at)
  WHERE status = 'running';

-- Fast lookup by client_request_id for idempotent enqueue.
CREATE INDEX IF NOT EXISTS idx_tasks_client_request
  ON tasks(client_request_id)
  WHERE client_request_id IS NOT NULL;

-- Cleanup queries for purgeCompleted.
CREATE INDEX IF NOT EXISTS idx_tasks_completed_at
  ON tasks(completed_at)
  WHERE status = 'completed';

-- ── Request ledger (dedup table) ───────────────────────────────────────────────

-- Mirrors the request-ledger pattern from memory-core for cross-instance
-- idempotency. When client_request_id is provided on enqueue, the task ID
-- is recorded here first; if the same key arrives again, the existing task
-- ID is returned instead of creating a duplicate.
CREATE TABLE IF NOT EXISTS request_ledger (
  client_request_id TEXT    PRIMARY KEY,
  task_id           TEXT    NOT NULL,
  t_created         TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  FOREIGN KEY (task_id) REFERENCES tasks(id) ON DELETE CASCADE
) STRICT;

-- ── Scheduler entries ─────────────────────────────────────────────────────────

CREATE TABLE IF NOT EXISTS scheduler_entries (
  id                TEXT    PRIMARY KEY,                          -- UUIDv4
  name              TEXT    UNIQUE NOT NULL,                      -- human-readable, unique
  task_type         TEXT    NOT NULL,
  payload           TEXT    NOT NULL DEFAULT '{}',                -- JSON
  cron_expression   TEXT    NOT NULL,
  priority          INTEGER NOT NULL DEFAULT 0,
  max_retries       INTEGER NOT NULL DEFAULT 0,
  ttl_ms            INTEGER,
  run_on_start      INTEGER NOT NULL DEFAULT 0,                   -- boolean
  enabled           INTEGER NOT NULL DEFAULT 1,                   -- boolean
  created_at        TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  updated_at        TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  last_enqueued_at  TEXT,
  last_error        TEXT
) STRICT;

CREATE INDEX IF NOT EXISTS idx_scheduler_enabled
  ON scheduler_entries(enabled, last_enqueued_at);
```

**Why `STRICT` tables:**
- Enforces column type affinity at the database level, catching type mismatches
  before they silently coerce. Matches `@adhd/sox-graph-store` convention.

**Why a partial index on `idx_tasks_dequeue`:**
- The dequeue query only ever needs tasks with `status IN ('queued', 'scheduled')`.
  A partial index is significantly smaller than a full index on `(priority, created_at)`
  because it excludes the majority of rows (completed, failed, running, cancelled).
- For a queue with 1M completed tasks and 100 queued tasks, the partial index is ~100 rows
  instead of ~1M rows. Faster dequeue, smaller memory footprint.

## 7. Enqueue semantics & idempotency

### Normal enqueue

```
enqueue(task)
    │
    ├── Generate UUIDv4 for task.id (if not provided)
    ├── INSERT INTO tasks (...)
    │
    ├── If clientRequestId provided:
    │     └── INSERT INTO request_ledger (client_request_id, task_id)
    │         ON CONFLICT(client_request_id) DO NOTHING
    │         If conflict → return existing task ID with deduplicated: true
    │
    └── Return EnqueueResult { id, deduplicated, isNew }
```

### Enqueue batch

```
enqueueBatch(tasks)
    │
    └── db.transaction(() => {
          for (const task of tasks) {
            enqueue(task)  // each enqueue runs inside the same transaction
          }
        })
```

All tasks in a batch are committed atomically. If any task fails (e.g., database
constraint violation), the entire batch is rolled back. This is critical for the
use case where a transaction must not partially commit (e.g., a multi-step
workflow where all tasks must be enqueued or none).

### Idempotency key (`clientRequestId`)

The `client_request_id` pattern mirrors `@adhd/sox-graph-store`'s dedup approach
and the `request_ledger` table in `memory-core`. The caller generates a unique key
(e.g., SHA-256 of the task payload + a sequence number) and passes it on enqueue.

**Contract:**
- If `clientRequestId` is null → normal enqueue, always inserts.
- If `clientRequestId` is provided → the enqueue is idempotent. A repeat with the same
  key returns the existing task's ID with `deduplicated: true` and does NOT create
  a new row.
- The ledger is NOT automatically pruned. The caller owns the dedup key namespace
  and should provide keys that are meaningfully bounded (e.g., per-day sequence,
  content hash). The ledger can be manually trimmed via `DELETE FROM request_ledger
  WHERE t_created < ?` if growth is a concern.

## 8. Dequeue & lease lifecycle

### Dequeue algorithm

```sql
-- Dequeue is executed inside a transaction.
-- 1. Find up to dequeueBatchSize eligible tasks.
-- 2. Atomically claim them (UPDATE + RETURNING).

BEGIN TRANSACTION;

UPDATE tasks
SET status            = 'running',
    started_at        = strftime('%Y-%m-%dT%H:%M:%fZ', 'now'),
    lease_expires_at  = strftime('%Y-%m-%dT%H:%M:%fZ', 'now', ? || ' seconds'),
    worker_id         = ?
WHERE id IN (
  SELECT id FROM tasks
  WHERE status IN ('queued', 'scheduled')
    AND (scheduled_at IS NULL OR scheduled_at <= strftime('%Y-%m-%dT%H:%M:%fZ', 'now'))
  ORDER BY priority DESC, created_at ASC
  LIMIT ?
)
RETURNING *;

COMMIT;

-- ? parameters: [heartbeatTimeoutSeconds, workerId, batchSize]
```

The `UPDATE ... RETURNING *` pattern is a single atomic operation. No other
consumer can see the same task. The transaction ensures the claim is committed
before the worker receives the task.

### Lease lifecycle

```
dequeue success
    │
    ▼
status = 'running'
lease_expires_at = now + heartbeatTimeoutMs
workerId = <worker>
    │
    ├── heartbeat() called before lease_expires_at
    │     └── lease_expires_at = now + heartbeatTimeoutMs (extended)
    │
    ├── complete() called
    │     └── status = 'completed', lease cleared
    │
    ├── fail() called
    │     └── retryCount < maxRetries → re-queued
    │         retryCount >= maxRetries → dead = true, status = 'failed'
    │
    └── lease_expires_at passes without heartbeat
          │
          ▼
        Reaper tick (every reaperIntervalMs):
        UPDATE tasks
        SET status = 'queued',
            lease_expires_at = NULL,
            worker_id = NULL,
            retry_count = retry_count + 1,
            scheduled_at = strftime('%Y-%m-%dT%H:%M:%fZ', 'now', ?)
        WHERE status = 'running'
          AND lease_expires_at <= strftime('%Y-%m-%dT%H:%M:%fZ', 'now')
          AND retry_count < max_retries
          AND (ttl_ms IS NULL
               OR (strftime('%s', 'now') - strftime('%s', started_at)) * 1000 < ttl_ms);
        --
        -- If retryCount >= maxRetries after increment:
        UPDATE tasks
        SET dead = 1,
            status = 'failed',
            completed_at = strftime('%Y-%m-%dT%H:%M:%fZ', 'now'),
            error = 'lease expired'
        WHERE status = 'running'
          AND lease_expires_at <= strftime('%Y-%m-%dT%H:%M:%fZ', 'now')
          AND retry_count >= max_retries - 1;  -- -1 because we're about to increment
        --
        -- If ttl_ms exceeded:
        UPDATE tasks
        SET dead = 1,
            status = 'failed',
            completed_at = strftime('%Y-%m-%dT%H:%M:%fZ', 'now'),
            error = 'task timed out (ttl_ms exceeded)'
        WHERE status = 'running'
          AND ttl_ms IS NOT NULL
          AND (strftime('%s', 'now') - strftime('%s', started_at)) * 1000 >= ttl_ms;
```

### Graceful shutdown behaviour

When `close()` or `pool.stop()` is called:

1. **Polling stops** — no new tasks are dequeued by this instance.
2. **Running tasks are NOT forcibly terminated** — the worker pool waits for
   running handlers to complete, up to `drainTimeoutMs`.
3. **If a handler completes after the drain timeout**, its `complete()` or `fail()`
   call will succeed (the database is still open during the drain phase). After the
   drain timeout, `close()` closes the database. Any handler still running will fail
   on its next database call with a `TaskQueueNotOpenError`.
4. **The lease expires naturally** — the reaper (in another process or the same
   process after restart) will re-queue the abandoned task. This is the safety net:
   no task is lost on shutdown, only delayed until the lease expires.

**Design rationale:** Forcibly terminating Node.js worker threads or Promises is
not safe — there is no portable mechanism to abort a synchronous `better-sqlite3`
call or an async I/O operation mid-flight. The lease expiry mechanism is the
correct safety net for crash recovery; graceful shutdown is a best-effort drain.

## 9. Retry with exponential backoff

### Backoff formula

When a task fails and is re-queued (`fail()` with retryCount < maxRetries), the
`scheduled_at` is set to:

```
backoffDelay = min(baseDelay * (2 ^ retryCount), maxDelay)
scheduled_at = now + backoffDelay
```

Where:
- `baseDelay` = 1,000 ms (1 second)
- `maxDelay` = 86,400,000 ms (24 hours)
- `retryCount` = the current attempt number (0-indexed, so first retry is `2^0 = 1s`,
  second is `2^1 = 2s`, third is `2^2 = 4s`, etc.)

| Attempt | backoffDelay |
|---------|-------------|
| 1       | 1 s         |
| 2       | 2 s         |
| 3       | 4 s         |
| 4       | 8 s         |
| 5       | 16 s        |
| ...     | ...         |
| 10      | 1024 s      |
| 16      | 65536 s     |
| 18      | 262144 s    |
| 20+     | 86400 s     |

The exponential backoff prevents thundering-herd restarts when a downstream
dependency (API, database, network) is degraded. The 24-hour cap ensures that
tasks never get stuck with a multi-year backoff due to a bug.

### Retry count semantics

`retryCount` starts at 0 (first execution). Each call to `fail()` increments it.
If `retryCount < maxRetries` after increment, the task is re-queued.
If `retryCount >= maxRetries` after increment, the task goes dead.

Example with `maxRetries = 3`:
- Execution 1 (retryCount=0): fail → increment to 1, re-queued.
- Execution 2 (retryCount=1): fail → increment to 2, re-queued.
- Execution 3 (retryCount=2): fail → increment to 3, `3 >= 3` → dead.
- Execution 1 (retryCount=0): complete → terminal with completed status.

### Lease expiry vs retry

If a lease expires (heartbeat miss), the reaper re-queues the task with
`retry_count = retry_count + 1`. This counts against the retry budget just
like an explicit `fail()` call. Reason: a heartbeat miss indicates the worker
is unresponsive — the task should be retried, but each miss consumes one retry
slot to prevent infinite re-queues on a permanently failing task.

## 10. Error taxonomy

```ts
// ── Base error ────────────────────────────────────────────────────────────────
class TaskQueueError extends Error {
  constructor(message: string, public readonly taskId?: string) {
    super(message)
    this.name = 'TaskQueueError'
  }
}

// ── Concrete errors ────────────────────────────────────────────────────────────

// Thrown when the queue has reached its maximum depth (if maxQueueDepth is configured).
// The caller should retry after tasks have been consumed.
class QueueFullError extends TaskQueueError {
  constructor(
    public readonly currentDepth: number,
    public readonly maxDepth: number,
  ) {
    super(`queue full: ${currentDepth}/${maxDepth}`)
    this.name = 'QueueFullError'
  }
}

// Thrown when a task operation (complete, fail, heartbeat, get) references
// a non-existent task ID.
class TaskNotFoundError extends TaskQueueError {
  constructor(taskId: string) {
    super(`task not found: ${taskId}`, taskId)
    this.name = 'TaskNotFoundError'
  }
}

// Thrown when complete() or fail() is called on a task that is not in 'running' status.
// Indicates a logic error in the worker — the task was already completed, failed,
// cancelled, or never dequeued.
class TaskNotRunningError extends TaskQueueError {
  constructor(
    taskId: string,
    public readonly currentStatus: TaskStatus,
  ) {
    super(`task ${taskId} is not running (status: ${currentStatus})`, taskId)
    this.name = 'TaskNotRunningError'
  }
}

// Thrown when fail() is called on a task that is already dead (maxRetries exhausted).
// This is defensive — if a worker receives this, its task was already declared dead
// by another worker (e.g., after a lease expiry race).
class TaskPermanentlyFailedError extends TaskQueueError {
  constructor(taskId: string, public readonly retryCount: number) {
    super(`task ${taskId} has permanently failed after ${retryCount} retries`, taskId)
    this.name = 'TaskPermanentlyFailedError'
  }
}

// Thrown when a background operation times out. Used by the scheduler when
// a cron-enqueue operation exceeds a deadline, and by the worker pool when
// drainTimeoutMs is exceeded during shutdown.
class TaskTimeoutError extends TaskQueueError {
  constructor(
    message: string,
    public readonly timeoutMs: number,
  ) {
    super(message)
    this.name = 'TaskTimeoutError'
  }
}

// Thrown when requeue() is called on a task that is not in a failed/dead state.
class TaskNotDeadError extends TaskQueueError {
  constructor(
    taskId: string,
    public readonly currentStatus: TaskStatus,
  ) {
    super(`task ${taskId} is not dead (status: ${currentStatus})`, taskId)
    this.name = 'TaskNotDeadError'
  }
}

// Thrown when deleteTasks() matches running tasks.
class QueueNotEmptyError extends TaskQueueError {
  constructor(public readonly runningCount: number) {
    super(`cannot delete: ${runningCount} tasks are currently running`)
    this.name = 'QueueNotEmptyError'
  }
}

// Thrown when the queue is used before open() or after close().
class TaskQueueNotOpenError extends TaskQueueError {
  constructor() {
    super('task queue is not open')
    this.name = 'TaskQueueNotOpenError'
  }
}

// Thrown on unrecoverable storage errors: disk full, SQLite I/O error, permission denied.
class TaskQueueSystemError extends TaskQueueError {
  constructor(message: string, public readonly cause?: Error) {
    super(message)
    this.name = 'TaskQueueSystemError'
  }
}

// ── Scheduler errors ───────────────────────────────────────────────────────────

// Thrown when a scheduler entry with the same name already exists.
class SchedulerEntryConflictError extends TaskQueueError {
  constructor(public readonly entryName: string) {
    super(`scheduler entry already exists: ${entryName}`)
    this.name = 'SchedulerEntryConflictError'
  }
}

// Thrown when a scheduler entry operation references a non-existent entry.
class SchedulerEntryNotFoundError extends TaskQueueError {
  constructor(public readonly entryId: string) {
    super(`scheduler entry not found: ${entryId}`)
    this.name = 'SchedulerEntryNotFoundError'
  }
}
```

## 11. Decisions log

| # | Question | Decision | Rationale |
|---|---|---|---|
| D-1 | Storage backend — SQLite vs in-memory vs Redis | **SQLite via better-sqlite3** | Durability is a first-class requirement. In-memory queues (p-queue, better-queue) lose all state on crash. Redis adds operational complexity (separate process, networking, auth). SQLite provides crash-safe durability with zero operational overhead — the queue lives in the same database as the application data. WAL mode allows concurrent reads during writes. See §6 schema. |
| D-2 | Dequeue strategy — SELECT FOR UPDATE vs UPDATE ... RETURNING | **UPDATE ... RETURNING in a transaction** | `SELECT ... FOR UPDATE` followed by a separate `UPDATE` is two round-trips with a window between them. `UPDATE ... RETURNING` is a single atomic statement that claims and returns in one operation. SQLite's serialized transaction model means no concurrent writer can observe uncommitted rows. This is the same pattern used by PostgreSQL-based job queues (graphile-worker, pg-boss). See §8. |
| D-3 | Heartbeat timeout as config vs per-task | **Config-level heartbeatTimeoutMs, shared across all tasks** | Per-task heartbeat would require the caller to estimate execution time at enqueue, which most callers cannot do accurately. A single cluster-wide timeout (default 30 s) is simpler and sufficient: long-running tasks call heartbeat() periodically; tasks that forget to heartbeat are re-queued. The `ttl_ms` per-task field is the escape hatch for tasks that should be killed on wall-clock time rather than heartbeat staleness. See §8. |
| D-4 | Retry backoff — fixed vs exponential vs linear | **Exponential with jitter, capped at 24h** | Exponential backoff prevents thundering-herd on downstream recovery. The cap prevents tasks from getting multi-year delays due to repeated retries. Jitter (randomizing the delay within [0.5*delay, 1.5*delay]) is deferred to implementation — it smooths the re-queue wave but adds complexity. The spec defines the base formula; jitter is additive. See §9. |
| D-5 | Running tasks on shutdown — force-kill vs lease- abandon | **Lease abandon (no force-kill)** | Node.js cannot safely abort a synchronous `better-sqlite3` call or an arbitrary async handler. `Promise.race` with a timeout does not cancel the losing Promise — it continues running (zombie handler). The lease expiry mechanism is the correct safety net: on restart, the reaper finds abandoned tasks and re-queues them. Graceful shutdown drains what it can within a timeout, then closes the database. See §8. |
| D-6 | Cron backend — node-cron vs croner | **croner** | `croner` is MIT-licensed, zero-dependency, correctly handles DST transitions and timezone offsets, and supports cron expressions with optional seconds. `node-cron` has unresolved DST bugs, bundles a patched `moment` dependency, and does not support timezone-aware scheduling. For a persistent scheduler where cron fidelity matters across DST boundaries, `croner` is the correct choice. See §5. |
| D-7 | Partial index for dequeue vs full index | **Partial index** (`WHERE status IN ('queued', 'scheduled')`) | A full index on `(priority, created_at)` includes millions of completed/running/cancelled rows that are never used by dequeue queries. A partial index is orders of magnitude smaller and produces the same query plan for the critical dequeue path. The trade-off is that listTasks with a status filter needs a separate index — hence `idx_tasks_type_status`. See §6. |
| D-8 | Queue depth limit — configurable vs unbounded | **Optional per-queue maxDepth via config** | Unbounded queues risk OOM on the `better-sqlite3` side if enqueue bursts exceed dequeue throughput by many orders of magnitude. A configurable `maxDepth` (default: 0 = unbounded) lets callers set a safety limit for bounded-resource scenarios. The `QueueFullError` is a backpressure signal to the enqueuer. Not the default because most use cases (CLI tools, embedded services) do not need a depth cap. |
| D-9 | Worker pool — single per-instance vs multi-pool | **Single pool per instance, but factory allows multiple** | A single `WorkerPool` per `TaskQueue` is the common case (one handler function). The factory pattern allows creating multiple pools on the same queue for different task type routes (e.g., one pool for high-priority tasks, one for low-priority). Each pool has its own concurrency and handler. The `dequeue` call is shared — all pools compete for the same eligible tasks. |
| D-10 | Dedup table (`request_ledger`) — ephemeral vs persistent | **Persistent in SQLite** | The ledger is in the same SQLite database as the tasks table. This ensures that dedup survives restarts (critical for the idempotent-enqueue contract). The ledger is append-only; the caller is responsible for pruning old entries. A persistent ledger also prevents duplicate enqueue across process restarts — a key requirement for CLI tools that may crash between enqueue and the next step. See §7. |
| D-11 | `result` field — string (JSON) vs blob vs separate table | **TEXT column storing JSON** | Task results are typically small (<1KB of structured data). A TEXT column is sufficient and avoids the join overhead of a separate results table. For large results (>64KB), the handler should store the result in a blob store and include a reference (hash or URL) in the result JSON. This keeps the tasks table lean. |
| D-12 | Scheduler entry uniqueness — by name vs by ID | **Both: name is UNIQUE for human convenience; ID is the PK** | The `name` field has a UNIQUE constraint to prevent accidental duplicate registration of the same cron entry (e.g., on restart of the scheduler). The `id` (UUID) is the stable foreign key for updates, deletion, and `triggerNow`. The scheduler does not auto-register entries on startup — they must be explicitly registered via `register()`. |

## 12. Metrics & observability

Same pattern as all `@adhd/*` packages — `console` logging with `[task-queue]` prefix
and instrumented counters.

### Logging contract

| Level | When | Example |
|---|---|---|
| `error` | Unrecoverable: SQLite corruption, disk full, fatal binding failure | `console.error('[task-queue] SQLite error during dequeue:', err)` |
| `warn` | Degraded-but-functional: lease expiry re-queue, reaper timeout, handler throws but task already dead | `console.warn('[task-queue] lease expired for task', taskId, '(re-queued, attempt', retryCount, ')')` |
| `info` | State change: queue opened/closed, scheduler tick started/stopped, pool started/stopped | `console.info('[task-queue] worker pool started (concurrency:', concurrency, ')')` |
| `debug` | Per-operation: enqueue/dequeue/complete/fail/heartbeat with timing | `console.debug('[task-queue] dequeue(', count, 'tasks) 3.2ms')` |

### Instrumented metrics

| Metric | Type | Labels | Description |
|---|---|---|---|
| `sox_tq_tasks_total` | counter | `type`, `action` | Lifetime task events: enqueue, dequeue, complete, fail, cancel, requeue |
| `sox_tq_queue_depth` | gauge | `type`, `status` | Current count of tasks per status (queued, running, etc.) |
| `sox_tq_processing_latency_ms` | histogram | `type` | Wall-clock time from dequeue to complete/fail |
| `sox_tq_queue_latency_ms` | histogram | `type` | Wall-clock time from enqueue to dequeue (time in queue) |
| `sox_tq_retry_count` | counter | `type` | Number of retries triggered (sum of all fail→re-queue events) |
| `sox_tq_heartbeat_misses` | counter | — | Count of tasks re-queued due to lease expiry |
| `sox_tq_ttl_kills` | counter | — | Count of tasks failed due to ttl_ms expiry |
| `sox_tq_scheduler_ticks` | counter | — | Total scheduler tick executions |
| `sox_tq_scheduler_enqueues` | counter | `entry_name` | Tasks enqueued by the scheduler, per cron entry |
| `sox_tq_pool_active` | gauge | `pool_name` | Current number of active handlers |
| `sox_tq_pool_queued` | gauge | `pool_name` | Current number of tasks pending in the pool's internal queue |
| `sox_tq_pool_drain_ms` | histogram | — | Duration of graceful shutdown drain phase |

Metric names use the `sox_tq_` prefix to namespace them within the `@adhd/sox-*`
ecosystem. The spec defines WHAT to instrument, not how — no specific metric SDK
is required.

### Lease reaper health

The reaper loop logs a warning if it encounters a task whose lease has been expired
for more than 5x the heartbeatTimeout. This indicates a systemic issue (reaper
was blocked, process clock jumped) rather than a single slow worker.

## 13. Spec gaps

> Items identified during design review as deferred. Separated into **spec-level gaps**
> (interface omissions) vs **implementation details** (belong in the package, not the spec).

---

### What belongs in the spec (deferred)

#### 1. Multi-process coordination

The current spec assumes a single-process deployment. Multiple processes sharing
the same SQLite database file can safely enqueue, dequeue, and complete tasks
(SQLite handles concurrent writes via WAL + busy_timeout). However:

- **No cross-process lease expiry notification** — a task abandoned by process A
  is not re-queued until the reaper in any process picks it up. This is acceptable
  (the reaper ticks every 5 seconds by default), but a notify-based approach
  (LISTEN/NOTIFY or a polling-efficient flag) would reduce latency.
- **No leader election for the reaper** — if two processes both run the reaper
  simultaneously, they double the re-queue check load but produce correct results
  (the `UPDATE ... WHERE` condition is idempotent; the second reaper will find
  zero rows to update). If both also run the scheduler, cron tasks may be enqueued
  twice. See gap #2 below.

**Resolution:** Document the idempotent-reaper property. Add a `reaperLeaderKey`
config option: when set, only the process holding the SQLite `app_lock` advisory
lock runs the reaper. Default: every process runs the reaper (safe but redundant).

#### 2. Scheduler leader election

When multiple processes run the scheduler, each process independently evaluates
cron expressions and enqueues tasks. Without leader election, every scheduler
tick produces N duplicate enqueues (one per process).

**Resolution:** The scheduler should acquire an advisory lock (`PRAGMA schema.approx_count_estimate`
or `sqlite3_exec("SELECT 1 FROM ...")` with a side-channel) before the tick eval.
Only the process that holds the lock should enqueue. If the lock holder crashes,
the lock is released automatically, and another process takes over on the next tick.
Implementation detail: use `better-sqlite3`'s `unsafeMode` or a separate `_lock`
table with heartbeat.

#### 3. Task reaping with priority escalation

Currently, a task that is re-queued due to lease expiry retains its original
priority. Some use cases benefit from **priority escalation**: a task that has
been retried N times should be dequeued ahead of fresh tasks to limit its
time-to-completion.

**Resolution:** Add an optional `priorityEscalation` config: when true, the
dequeue query adds `MAX(priority, (retryCount * escalationFactor))` as the
sort key. The reaper can optionally bump a re-queued task's priority.
Default: false (unchanged priority).

#### 4. Complex task workflows (DAG dependencies)

The current spec supports only independent tasks. There is no mechanism for
task dependencies ("task B runs after task A completes"), fan-out ("enqueue
one task that fans out to 10 subtasks"), or fan-in ("wait for all 10 subtasks
to complete before proceeding").

**Resolution:** Defer entirely. DAG workflows are a significant design surface
(see: Temporal, Airflow, Prefect) and are not required by any of the three
primary use cases. If DAG support is needed, it should be a separate package
(`@adhd/sox-workflow`) that builds on top of `@adhd/sox-task-queue`.

#### 5. Dead task alerting

When a task goes dead (maxRetries exhausted), the current spec stores the error
and sets `dead = 1`. There is no alerting mechanism (webhook, callback, log
aggregation).

**Resolution:** Add an optional `onDead` callback in `TaskQueueConfig`:
`onDead?: (task: Task) => void`. Called synchronously when a task transitions
to dead. The caller can log, emit a metric, or enqueue an alert. The callback
must not throw (errors are caught and logged at `warn` level).

---

### What belongs in the implementation, not the spec

**Specific retry jitter algorithm** — the spec defines exponential backoff with
a 24h cap. The specific jitter function (full jitter vs equal jitter vs decorrelated
jitter) is an implementation detail. The default should be full jitter:
`sleep = randomBetween(0, min(cap, base * 2^retryCount))`.

**Poll interval sleep mechanism** — the worker pool's `pollIntervalMs` sleep
between dequeue-with-no-results is implementation-defined: `setTimeout`,
`setInterval`, or an async `sleep()` utility. The spec does not mandate a mechanism.

**Cursor-based pagination for `listTasks`** — the current `TaskFilter` uses
`limit` + `offset`. For large queues (>1M tasks), offset pagination is slow
(SQLite must scan and skip rows). A future implementation may add cursor-based
pagination (`after`/`before` with a composite cursor on `(priority, created_at, id)`).

**Reaper tick scheduling** — the reaper runs on `setInterval(reaperIntervalMs)`.
The spec does not mandate how the interval is managed (e.g., drift correction,
exact timing). The implementation should use a simple `setInterval`.

**Schema migration strategy** — the schema includes `CREATE TABLE IF NOT EXISTS`
and `CREATE INDEX IF NOT EXISTS`. The implementation should version the schema
via a `_schema_version` table (matching `@adhd/sox-graph-store` convention) to
support forward-compatible migrations.

**WAL checkpointing** — the implementation should periodically issue
`PRAGMA wal_checkpoint(TRUNCATE)` during idle periods to prevent WAL files from
growing unbounded. The spec defines WAL mode as the journal; the checkpoint
schedule is a tuning parameter.
